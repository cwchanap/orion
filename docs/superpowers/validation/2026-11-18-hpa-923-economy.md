## Text-scale coverage

**Browser check performed (round 2).** Method: the Flutter web engine
derives `MediaQuery.textScaler` from the HTML root's computed font size
and re-lays out on change. At 320 x 568 the `FIRST CLEAR` semantics node's
bounds measured 157.8 x 14 px; setting
`document.documentElement.style.fontSize='32px'` (from the 16px default →
expected scale ~2.0) reflowed the sheet and re-measured the node at 29 px
tall (~2.07x, including line-height growth) — the engine honors the root
font size, so the earlier claim of a fixed 1.0 was wrong. The post-fix
stacked rows hold complete labels at that scale:
[briefing-nebula-scrip-320-textscale2x.jpg](hpa-923-evidence/briefing-nebula-scrip-320-textscale2x.jpg).
(Note: DPR 2 is device pixel ratio, not text scale — distinct axes.)

Deterministic coverage:
`test/widget/stage_briefing_sheet_test.dart` pumps the sheet at 320 x 568
with 1x, 1.5x and 2x `MediaQuery.textScaler` and asserts every Scrip label
renders whole (no ellipsis, single text box). RED chronology: the newly
added 1x/1.5x cases failed on the pre-fix code (`FIRST CLEAR` ellipsized);
the 2x case and the breakpoint-width regression
(`scrip labels stay whole at the column-breakpoint width`, 352px viewport
inside the old-vs-new threshold window) were added alongside — the
breakpoint test failed precommit against the 18px-inset math and passed
after the 21px correction; the wide `three-across at the product viewport`
assertion passed both before and after.

## Deviations and blockers

- **MCP profile lock:** `new_page`/`list_pages` initially failed because
  Chrome was already running on the MCP default profile
  (`chrome-profile`); the server recommends `--isolated` for parallel
  instances. Work continued on the already-open page, which reports
  `isolatedContext=hpa-923-task7-acceptance`. Storage writes were confined
  to this context; unrelated keys were enumerated and preserved.
- **Screenshot filePath:** MCP `take_screenshot`'s `filePath` parameter
  rejects every write target tried (repo path, `/tmp`, relative path,
  Chrome profile dir — "Access denied", outside the MCP server's
  configured workspace roots). Workaround used for the committed browser
  captures: query the Flutter canvas with `canvas.toDataURL('image/jpeg')`
  via `evaluate_script`, return the base64 payload, decode it locally into
  `hpa-923-evidence/`. This is real raster output of the live browser page,
  distinct from the `ORION_CAPTURE_DIR` widget fixture
  (`fixture-1b.png`, which is test-harness output, not browser).
- **Compact fix not present during first live run:** the running debug
  server predated the fix, so the pre-fix truncation was reproduced live
  (valuable: it confirmed the defect). DTD `hot_reload` then applied the
  fix and the 320 x 568 capture was retaken showing the collapsed layout.
- **Single-pull in the isolated save:** the round-2 evidence pull
  recruited Sayo Kitami (D), `1 FLARE FIRED`, `+0 Scrip`, balance 235 →
  135; roster 5/12. The isolated context's progress document now reads
  `scrip 135, ownedCharacters {haruto:2, mio:2, rin:1, tetsuo:1, sayo:1},
  squad [haruto, mio, tetsuo]`.
- **Endless tie:** the second endless loss reached wave 3 → `Best result
  already saved.` (`Best: 2 waves`) — the run tied, not improved, the
  recorded best so no save write occurred; still no Scrip line
  ([mission-report-endless-390.jpg](hpa-923-evidence/mission-report-endless-390.jpg)).
- **Game speed in automation:** waves were played at 2x/3x; ~2-3 minutes
  wall time each in the emulated page.
- Fresh-profile `0 Scrip` Flare screen was re-exercised in round 2
  (campaign key removed, app reloaded → 0-Scrip profile, both CTAs
  disabled; capture linked above). The same underfunded disabled state was
  additionally verified at funded-but-insufficient balances: 385 (Fire 10)
  and 85/65 (Level Up).
- Old background-art differences vs the artboards are accepted until
  HPA-926, as recorded in the task ledger.
